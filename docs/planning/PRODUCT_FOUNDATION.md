# OUTPERFORM — Product Foundation

## North star

OUTPERFORM is the place people take work when they want to know how much better it can become.

## Product definition

A universal AI work-improvement and verification platform. It accepts work at any lifecycle stage—from an early idea to an existing deliverable—then improves it through a controlled, evidence-backed workflow.

## Core loop

1. Understand the user's intended outcome, context and constraints.
2. Preserve an immutable baseline.
3. Define explicit, task-specific acceptance criteria.
4. Execute a primary attempt or inspect existing work.
5. Select challenge methods based on expected value, risk and budget.
6. Generate independent alternatives or adversarial findings where useful.
7. Adjudicate findings using evidence, not model consensus.
8. Implement accepted improvements with appropriate approval.
9. Verify the result and detect regressions.
10. Deliver the artifact, changes, evidence and remaining uncertainty.

## Distinctive challenge layer

Psychological/competitive framing—including competitive provocation, reverse framing, confidence challenges and second-look challenges—remains a first-class experimental strategy family. These are prompt interventions, not evidence that models possess human emotions. Their effects must be tested against ordinary revision and independent-review controls.

## Product is not

- a generic chatbot;
- a model leaderboard;
- a model tournament;
- a prompt library;
- an agent framework sold as an outcome;
- a dashboard that scores work without improving it.

## Product principles

Outcome-first; universal intake; baseline preservation; independent evaluation; evidence-backed adjudication; approved implementation; regression testing; budget awareness; provider interoperability; privacy by default; honest uncertainty.

## First proof

A real code task and a real document/research task should eventually pass through the full loop. The initial engineering slice should prove one complete path before breadth is added.

## Status discipline

Every claim must be labelled accurately: planned, implemented, tested, deployed or independently verified. No mock data or static UI may be used as proof of a working capability.
